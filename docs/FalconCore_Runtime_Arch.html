Agent 从配置、部署、认领 Run 到 Planner / Tool Loop 执行的统一说明
版本 v3.0｜2026-08-06｜以当前 src/vnext/ 实现为准

阅读主线：配置定义 Agent → Deployment 固定 revision → 外部平台启动 AgentInstance → Gateway 创建并分配 Run → Instance 认领并发起一次顶层执行 → Gateway 组装上下文并选择普通 Tool Loop 或 Persistent DAG Planner 路径 → 共享 Capability Dispatch → Instance 提交终态。
文档口径：已实现 表示当前代码路径；条件启用 表示只有发布配置和本轮输入命中时生效；设计中 表示不得按已上线能力理解。

二、配置、部署与启动

2.1 从 Agent 定义到可运行实例

Draft AgentConfig
  → publish immutable AgentConfigSnapshot(revision)
  → create AgentDeployment(agentId + configRevision + runtime/scaling)
  → generate Docker/K8s/local manifest
  → external platform starts AgentInstance
  → Instance register + heartbeat
  → confirm desiredConfigRevision readiness
  → Ready Instance can receive capacity reservations

markRuntimeBundleLoaded() 是 readiness 状态标记，不表示 Instance 下载或持有 Prompt、Model、Tool 等 Bundle 内容。真正的 Bundle 仍由 Gateway 按 Run 构造。

2.2 冷启动顺序与保护语义

顺序动作为什么必须存在
1初始化 PostgreSQL stores、Redis online/capacity/streaming stores、Provider/Secret stores调度、幂等和 active-active 事件不能依赖进程内临时状态
2组装 Capability Registry、Executor、MCP ProviderRun 开始前必须得到确定的有效 Capability directory
3启动 RuntimeGateway HTTP/SSE 与 reconciler/worker loops先具备 Run、心跳和恢复能力，再接受 worker
4AgentInstance 注册，获得 sessionId/sessionToken、leaseDurationMs、desiredConfigRevision建立认证、租约和 deployment 绑定
5Instance ready heartbeat 后递归轮询 assigned runs避免未准备实例占用容量
6每个 Run 被 claim 后才启动 250ms cancellation monitor，Run 结束即停止取消监控属于 attempt 生命周期，不是全局后台任务

三、一次 Run 的端到端生命周期

3.1 唯一主流程

① 入口与创建：Client 使用 POST /runtime/runs，或 Chat Facade 使用 POST /v1/chat/stream。Gateway 创建状态为 queued 的 Run，并写 SessionRunLedger。
② 分配：Gateway 根据 deployment、Ready Instance、HotSession sticky routing 和 Redis Lua capacity reservation 尝试分配。只有预留成功才进入 assigned；否则保持 queued 或返回 no_capacity。
③ 拉取与认领：Instance 调用 /runtime/instances/:instanceId/runs/assigned 拉取，再调用 /runtime/runs/:runId/claim。Gateway 校验 session、assignment 和 active attempt，状态进入 running。
④ 输入与上下文：text Run 先追加 user_input Transcript，再调用 /context/assemble。Instance 不在本地拼 Prompt。
⑤ 一次顶层执行：Instance 只调用一次 /model/invoke 或 /model/stream。多轮模型调用、Planner 和 Tool Loop 全部发生在 Gateway 内部。
⑥ 输出与完成：Gateway 返回最终结果；Instance 追加 assistant_output，再调用 /complete。Gateway 推进终态、释放 Redis capacity 并尝试 drainQueuedRuns()。

3.2 三种 modality

modalityInstance 路径是否进入模型执行引擎
textuser_input → context → model invoke/stream → assistant_output → complete是；见第四章
tool直接调用 Run-scoped Tool HTTP proxy → complete否；仍进入第五章的共享 Capability 安全管线
skill直接调用 Run-scoped Skill HTTP proxy → complete否；仍受 registry/exposure/budget 约束

3.3 Context 的单一装配入口

TranscriptBackedRunContextAssembler.assemble() 是模型可见上下文的唯一入口。它把持久化事实与本次模型窗口分开处理：

  1. 读取有界、按 session/chatScope 过滤的 Transcript 候选窗口，并做 rollback、canonical attempt 和 incomplete-tool 清洗。
  2. 按已发布策略条件性检索 UserPreferences 和 Memory；未启用 policy/retriever 时不参与。
  3. 计算 maxInputTokens = maxContextTokens - reservedOutputTokens - nativeToolContextTokens。
  4. 按 Prompt、当前用户输入、Preferences、Memory、History/Summary 的约束生成模型可见 messages。
  5. 只有预算不足且存在 omitted history 时才进入 Compaction/Summary；可复用 replacement checkpoint。
  6. Tool schema 和 prompt-only Skill instructions 不由 Assembler 附加，而由后续执行引擎 payload builder 加入。

3.4 Chat SSE

Chat Facade 在执行期间并发桥接 Redis StreamingEventChannel，不是在 Run complete 后一次性回放。对外事件为 started → activity/message → done，失败时为 error；Provider 的 delta 是内部事件/字段。原始 /runtime/runs API 不自动返回 Chat SSE。

四、Agent 执行引擎：Planner 与 Tool Loop

4.1 共同入口与模式判断

4.2 普通模式

  • 普通模式不调用 Planner。Gateway 将完整有效 Capability surface 暴露给主模型，决策所有者是 main_model。
  • 同一 model step 可以返回一批调用。只有 allowParallelTools=true、全部为 Tool、全部 readonly 且每个 Tool 声明支持并行时才并行；其他批次顺序执行。
  • 无 tool calls 不必然立即结束：可接受文本、执行零工具语义恢复、做一次 required-tool retry，或进入 post-tool finalization。
  • Provider retry/failover 只允许在流提交前按既有策略进行；Tool retry 是第五章独立规则。

4.3 Persistent DAG 模式 条件启用

  • 仅当发布的 runtime.planner.mode="dag" 且 DAG definition 适用于本轮 requestText 时启用。
  • 要求 Runtime Capability Registry、durable Transcript 和 authoritative Persistent DAG resolver；缺失时 fail closed。
  • Planner 持久化 RuntimePlannerDagPlanRecord，steps 内嵌在单表 state JSONB；不是 ExecutionRun/Plan/Step 三表模型。
  • Planner 输出当前 node 的 scope、override、requireToolCall 和边界；Tool result 作为 evidence 推进 transition/replan。
  • DAG 要求单 Capability 执行，不允许 parallel tools；Planner admission/dispatch fence 不是用户写授权。

4.4 两条路径共享什么

两条路径都进入 runBoundedNativeToolLoop() 和第五章的单次 Tool Dispatch。Planner 只能收窄或强制当前 scope，不能绕过 schema、authoritative permission、write-intent、预算、Transcript、去重和错误分类。

五、Capability 与单次 Tool Dispatch

5.1 Capability 从哪里来

来源注册/暴露方式执行方式
内建 ToolCapability definition + AgentConfig exposure + runtime availabilityLocal Executor 或 Provider adapter
内建 Skillexecutable Skill 或 prompt-only SkillinvokeSkill()；prompt-only 只注入 instructions
MCP Tool启动期 eager discovery/注册；每个 Run 按 agent/role allow/deny 动态追加 exposure与内建 Tool 共用 Dispatch，最终调用 MCP provider
subagents / sessions_spawn已注册能力；为同一 Agent 派生带角色覆盖的隔离子会话不是调用另一个固定 Agent Deployment
CallableAgent设计中当前不可按已落地跨 Agent RPC 使用

MCP 当前支持 stdio 和 streamable-http；配置来自 FALCONCORE_MCP_SERVERS_JSON，不属于 AgentConfig。safe name 使用 server__tool 形式，真正调用时再映射回原始 toolName。

5.2 单次 Dispatch 的权威顺序

阶段真实行为失败语义
1. Capability match在已经物化并暴露给本轮模型的 native surface 按 name 匹配，再加载 Registry definition未注册/未暴露 → TOOL_CALL_REJECTED
2. Arguments/schema规范化参数并按 inputSchema 校验；Provider tool call 在允许时可做一次有界修正仍不合法 → REJECTED
3. Permission/intentRegistry definition + pinned exposure 解析 authoritative permission；write/dangerous 需要绑定 runId、toolName、本轮 requesterText 的 writeIntentGrant，并检查负向意图、非空写参数和 required inputs任一条件失败 → REJECTED
4. Transcript identity校验 toolCallId identity/conflict；readonly completed 结果可以回放冲突或非只读重复 → DUPLICATE_TOOL_CALL_BLOCKED
5. Admission普通模式非 readonly Tool 获取 durable claim；readonly/Skill 跳过。Persistent DAG 改用 planner fenceclaim 冲突/不可确认 → fail closed
6. Before executereserve in-flight counter、append tool.call；有 claim 时标记 dispatching预算或持久化失败时不执行 Capability
7. Execute/classifyTool → Provider/CapabilityExecutor；Skill → invokeSkill；完成后 commit/rollback counter按 transient/permanent/unknown_write_outcome 分类
8. Evidence/result追加 tool.result 或 tool.error，更新 claim 终态并格式化回传模型由 failurePolicy 决定继续、收尾或终止

5.3 Durable claim、retry 与未知写结果

  • 普通模式的非 readonly Tool 使用独立表 falconcore_runtime_tool_dispatch_claims；claim identity 为 runId + toolName + dedupeScope + normalized arguments，不含 toolCallId。
  • readonly Tool 只有在 runtime retry policy 已配置且错误可重试时才重试，maxAttempts 封顶 3；write/dangerous 只尝试一次。
  • 超时来自 Capability exposure 的 timeoutMs 与 Run deadline，不存在统一默认 maxToolMs。
  • 非只读调用 dispatch 后被取消时可能成为 unknown_outcome：禁止自动重试，Run 失败，durable claim 保持待对账状态。

六、Provider 调用与流式边界

6.1 Route、Binding 与 failover

Gateway 在实际 Provider 调用阶段解析 binding 和 credential；RuntimeBundle 不包含 credential。候选按 RouteConfig 和 providerBindingRefs 顺序遍历，并校验 modality、availability 和 quota。

错误分类行为
request请求内容错误，立即抛出，不切换候选
account / model / binding记录对应层级不可用，并跳过同层候选
transient网络、5xx、429、并发限制、断路器等，可继续下一个候选
stream committed / abort / quota terminal禁止继续 failover，避免重复或破坏流语义

6.2 两层资源保护

层作用域保护
ProviderOperationGuardprovider + account并发、排队、等待上限、transient circuit breaker、create-stage bounded retry
ProviderQuotaGatebindingbinding-scoped concurrency 和 rate admission
不要混淆三种 retry：Provider create-stage retry、Provider binding failover、readonly Tool retry 是三套不同机制；它们的作用域、停止条件和副作用风险不同。

七、Run 状态机、并发与故障恢复

7.1 状态生命周期

queued
  └─ capacity reserved → assigned
       └─ active Instance claim → running
            ├─ normal completion → completed
            ├─ execution failure → failed
            ├─ explicit cancellation → cancelled
            ├─ terminal recovery decision → interrupted
            └─ lease lost → recovery_pending → queued（最多一次恢复）

completed、failed、interrupted、cancelled 是不可逆终态。迟到结果可以作为审计证据保存，但不能重新推进 Run。

7.2 并发一致性保护

风险保护
两个 Gateway 同时分配容量Redis Lua 原子 reserve/release；assignment 写入 SessionRunLedger
旧 Instance/旧 attempt 提交结果session ownership + activeAttemptId 校验
worker 崩溃后重复执行lease reconciler、recovery count、Transcript identity、非只读 durable claim / DAG fence
并行写扩大副作用write/dangerous 顺序执行；DAG 禁止 parallel tools
取消与 Tool dispatch 竞争执行前可取消 claim；dispatch 后非只读结果不确定时进入 unknown_outcome
多 Gateway SSERedis StreamingEventChannel；终态事件和 Run ledger 共同约束结束语义

7.3 Recovery 边界

  • running Run 的 Instance lease 过期后可进入 recovery_pending，随后由 recovery 流程重新进入 queued。
  • 同一 Run 再次丢失 Instance 时进入 terminal interrupted，避免无限恢复和资源放大。
  • 普通执行 attempt 的上限不是无条件 claim retry；第二次 attempt 只用于特定 requeue/recovery 路径。
  • 任何恢复都不能自动重试 unresolved non-readonly side effect。
