一、系统边界、核心对象与权威来源

二、配置、部署与启动

2.1 从通用模型到可运行 Agent：完整生命周期

FalconCore 不通过复制模型来创建 Agent。模型提供通用理解与生成能力；AgentConfig 把项目身份、工作规则、可访问能力和运行边界固定成版本；Deployment 再把该版本关联到可运行的通用 AgentInstance。

① 准备外部依赖
   Provider Binding + 已实现并注册的 Tool/Skill
        ↓
② 创建 Agent Draft
   Prompt + Model route + Capability exposure + Runtime limits
        ↓ Publish
③ AgentConfigSnapshot（不可变 revision）
        ↓ 创建或同步
④ AgentDeployment
   agentId + configRevision + runtimeKind + image/resources/Gateway address
        ↓ 由 Docker / Kubernetes / Local 外部启动
⑤ AgentInstance（通用 worker）
   register → heartbeat → revision Ready → claim Run
        ↓
⑥ RuntimeGateway 执行
   读取 revision → 组装 Prompt/Capability → 调用模型 → Dispatch → Transcript
对象回答的问题不负责什么
AgentConfig这个 Agent 是谁、怎样判断、能看到哪些能力、执行怎样受限？不安装 Tool、不开容器、不保存 Provider credential
AgentConfigSnapshot某个已发布 revision 的完整运行合同是什么？发布后不可修改；新变更必须生成新 revision
AgentDeployment哪个 revision 以何种 runtime、资源和容量运行？不包含 Prompt、Tool executor 或完整 RuntimeBundle
AgentInstance哪个通用 worker 在线、Ready，并可承接多少 Run？不拥有项目 Prompt、模型调用或 Capability 实现；这些由 Gateway 按 revision 解析
核心边界：配置 Agent、实现 Capability 和启动计算资源是三个独立动作。AgentConfig 选择能力；Registry/Executor 提供能力；AgentDeployment 和 AgentInstance 提供运行容量。

2.2 Agent 专业化配置：每项配置何时生效

一个项目 Agent 的差异主要来自 Prompt、模型路由、Capability exposure 和响应要求。以下表格同时说明“配置有什么用”和“它不能替代什么”。

配置作用运行时投影边界
agentId / name / description标识 Agent 并说明责任范围agentId 关联 Draft、revision、Deployment、Run 和审计；名称与描述主要用于管理和发现ID 应稳定；修改名称不会改变 Capability 权限
systemPrompt定义身份、目标、成功标准和长期边界发布时必填；通常作为 system message 进入每次 Agent Invocation，受控轻量阶段可显式抑制或覆盖不能授予数据库/API 权限，也不能证明动作已经执行
developerPrompt定义项目流程、判断规则、澄清和异常处理基础 Provider 投影保留 developer role；Capability Harness Conversation Context 当前以 system message 装配不要依赖所有执行路径都使用相同 Provider role
instructionBlocks[]将响应要求、合规规则或阶段说明模块化仅装配 enabled=true 且内容非空的 block；重复内容会被抑制并记录 diagnosticsorder 是配置顺序元数据；不要把 block 当成权限或状态门控
model选择 Provider、模型、候选路由及生成参数revision 固定路由合同；Gateway 调用时通过 Provider Binding 解析可用 account/credentialcredential 保存在 SecretStore，不进入 AgentConfig 或 RuntimeBundle
tools[]声明该 Agent 可暴露的内建或显式固定 ToolRun 时与 Registry definition、availability、authoritative permission 和当前 scope 求交集只是 exposure，不会安装实现；配置 permission 不能高于 Registry 权威值
skills[]启用领域方法或可调用复合能力按 Skill metadata 进入 Prompt channel、native Capability channel 或 output/post-tool transformPrompt-only Skill 不等于 Tool；callable Skill 仍受 schema、scope 和预算约束
Response Contract约束最终回答的结构、语气和失败表达Admin UI 将 instructions 写入 instructionBlocks[id=response_contract]，将 mode/name/schema 保存到 metadata.responseContract当前没有通用 JSON Schema 强制校验器；它不能替代 output transform、权限或真实证据
metadata保存管理信息和已有消费者约定的扩展键只有被 Runtime 明确读取的键才影响执行任意 metadata 不会自动进入 Prompt，也不会自动成为 policy gate
项目交付 Agent 示例：System Prompt 固定职责和事实边界；Developer Prompt 定义风险升级与验收方法；readonly Tool 查询工单和代码状态；write Tool 创建任务；Skill 注入 Review 清单；Response Contract 规定“摘要、证据、风险、下一步”。模型负责判断下一步，只有持久化 Tool result 能证明外部系统已被读取或修改。

2.4 Tool/Skill 的实现、注册、暴露与部署

在 Agent 页面勾选 Tool/Skill 只是在 revision 中声明 exposure。模型真正能够调用一项能力，还要求实现、Registry、availability 和当前 Run scope 同时成立。

A. 提供实现
   内建代码 / Skill package / MCP Server
        ↓
B. 注册能力
   Definition + description + schema + permission + Executor/Provider + availability
        ↓
C. 暴露给 Agent
   AgentConfig exposure；MCP 还可按 server agent/role policy 动态追加
        ↓
D. 构建本轮 Effective Scope
   revision exposure ∩ registered ∩ available ∩ role/policy ∩ 普通或 DAG node scope
        ↓
E. Shared Capability Dispatch
   schema → authoritative permission → write-intent → dedupe → budget → Executor/Provider → Transcript
能力来源实现与部署如何对 Agent 生效
内建 Tool在 FalconCore 中提供 ToolDefinition、schema、Executor/Provider 和 availability；变更后重建并部署 RuntimeGateway从 Capability 列表加入 Agent Draft 并 Publish；Run 时再次计算 effective scope
MCP Tool独立部署 MCP Server；Gateway 通过 FALCONCORE_MCP_SERVERS_JSON 的 stdio 或 streamable-http 配置发现和调用可以在 AgentConfig 显式固定，也可能按 server agent allow/deny 与 subagent role policy 动态追加
Prompt-only SkillSkill package 提供 instructions/metadata，由 Gateway loader/materialization 读取启用后只向当前允许 scope 的 Prompt channel 注入说明
Callable Skill除 instructions/native schema 外，还需注册 Skill executor 及其依赖启用后可进入 Prompt 和 native Capability channel，执行仍经过共享 Dispatch

新增 Capability 的代码验收顺序

  1. 实现：定义稳定输入、输出和失败语义；有外部副作用时明确幂等与 unknown outcome。
  2. 注册 Definition：提供唯一名称、描述、输入 schema、权威 permission 和 metadata。
  3. 注册 Executor/Provider：prompt-only Skill 除外；依赖缺失时 availability 必须为 false 或 fail closed。
  4. 暴露并发布：内建能力加入 Agent Draft；MCP 还可由 server policy 提供候选 exposure。
  5. 执行验证：检查 schema、permission、write-intent、budget、dedupe、真实 result/error 和 Transcript。

内建能力的集中入口包括 default-capability-definitions.ts、default-capability-executors.ts 和 default-capability-availability.ts；MCP Definition/Provider 由 Gateway 启动期 catalog/discovery 注册。

部署边界：AgentInstance 镜像只实现通用 worker 和 Run proxy 合同。Prompt、Provider credential、Capability Registry、Executor 和模型/工具 Dispatch 均由 RuntimeGateway 持有；Deployment 的 capabilities 是 worker 可承接的运行类别，不是 AgentConfig 的逐项 Tool/Skill exposure。

2.5 创建 Draft 并发布不可变 revision

  1. 确认能力已就绪：通过 GET /admin/capabilities 检查所需 Tool/Skill 已 registered 且 available；AgentConfig 不能创建不存在的能力。
  2. 创建 Draft：在 Agents 中创建稳定 Agent ID，填写 Name、Description 和必需的 System Prompt。
  3. 完成专业化配置：填写 Developer Prompt、Instruction Block/Response Contract，选择最小 Tool/Skill 集合并设置有界 Runtime 参数。
  4. 连接模型：在 Providers 中创建或验证 Provider Binding，将 provider/model route 写回 Draft；credential 只保存在 SecretStore。
  5. 保存 Draft：Draft 可以继续编辑，保存成功不代表 Runtime 已采用该配置。
  6. Publish：ControlPlane 校验字段、Capability/permission、Provider Binding、Runtime budget，以及适用时的 DAG definition/manifest。
  7. 获得 revision：Publish 生成不可变 AgentConfigSnapshot.revision；正在执行或已经创建的 Run 继续使用其固定 revision。
Response Contract 的真实存储：UI 中的最终响应 instructions 会成为 response_contract Instruction Block；mode/name/schema 位于 metadata.responseContract。两者用途不同，不应描述成一个独立的 AgentConfig 一级字段。

2.7 上线验收：用同一个 Run 证明配置已经生效

Draft、Publish、Deployment 和 Instance Ready 分别只证明生命周期中的一个阶段。上线完成必须沿同一个 Run 同时验证配置版本、模型可见内容、Capability scope 和持久化执行证据。

证据组必须确认失败时定位
配置与容量Run 固定到预期 agentId + revision；Deployment 指向该 revision；承接 Instance 为 ReadyPublish 结果、Deployment 自动同步、register/heartbeat、desired/loaded revision
Prompt 与上下文Prompt diagnostics 包含预期 System/Developer/Instruction Block，以及当前 scope 允许的 Skill instructionsenabled/content、重复抑制、受控 Prompt override、Skill materialization
Capability surface所需 Tool/Skill 同时 registered、available、exposed；模型只看到当前 iteration/DAG node 允许的 native schemaDefinition、Executor/Provider dependency、AgentConfig、MCP policy、DAG scope
Dispatch 与证据readonly 正常执行；真实 write/dangerous 通过 authoritative permission 和本轮 write-intent；Transcript 有匹配的 call/result/errorschema、permission、writeIntentGrant、budget、dedupe/claim、toolCallId 和 unknown outcome
最终输出回答基于本轮真实 evidence，并经过有效 post-tool/output transform 和命中的 RuntimeVisibleOutputPolicy模型是否虚构执行、post-tool continuation、output protocol、policy appliesTo(run)
可选 DAG未命中时不存在 DAG node/claim/transition；命中时 resolver 只开放当前 node Capability，并持久化状态推进planner.mode、definition root condition、requestText、DAG state 和 Transcript evidence
验收结论：Draft 保存成功 ≠ revision 已生效；Publish 成功 ≠ Instance 已运行；Instance Ready ≠ 项目能力正确。至少保存 Run ID、固定 revision、Prompt diagnostics、effective Capability snapshot、Transcript events 和最终输出，才能证明 Agent 已按项目合同运行。

三、一个 Session 如何运作：多轮、调度、上下文与连续性

本章的 Session 指用户可感知的逻辑对话范围。它不是某个容器中的常驻 Agent，也不是 AgentInstance 注册返回的物理 sessionId。逻辑 Session 通过多个独立 RuntimeRun 延续；每个 RuntimeRun 内再发生一次第四章的 Agent Invocation。

3.1 先拆开三种 Session 和两个执行对象

四、一个 Agent 如何运作执行：从 pinned Bundle 到最终输出

4.1 AgentInstance 与 RuntimeGateway 如何共同完成一轮

AgentInstance 是 Run worker，不是智能循环的宿主。它持有当前 registration session 和容量，在 claim 后根据 modality 调用 Gateway；RuntimeGateway 才读取 pinned RuntimeBundle、装配模型输入、运行 Capability Harness、调用 Provider/Executor 并形成可持久化结果。

  → text: append user_input → assemble context → invoke/stream model

  → resolve owned RuntimeRunRecord + pinned RuntimeBundle

4.3 基础 Context 与 Prompt 的权威装配

TranscriptBackedRunContextAssembler.assemble() 构造基础 Session Context；Capability Harness 随后按当前 execution scope 增量加入 Skill instructions、native Capability schema 和本轮 Tool evidence。因此 ContextAssembler 是基础上下文入口，但不是所有模型可见信息的唯一生产者。

  1. 优先按逻辑 Chat Scope（agentId + user + threadId）查找该对话的多个 Run，再跨这些 Run/物理 assignment session 读取 Transcript；缺少 Chat Scope 时才退化为当前物理 assignedSessionId。
  2. 对候选历史清洗 rollback、非 canonical attempt 和不完整 Tool exchange，避免失败或被替换 Attempt 的内容重新进入模型上下文。
  3. 按已发布 Memory policy 条件性检索 UserPreferences/Memory；没有 policy、retriever 或权限时不参与。
  4. 计算 maxInputTokens = maxContextTokens - reservedOutputTokens - nativeToolContextTokens。
  5. 组合 System/Developer Prompt、Instruction Blocks、当前用户输入、Preferences、Memory 和 History/Summary。
  6. 只有预算不足且确实省略了历史时才触发 compaction/summary；replacement checkpoint 可以复用。

  • readonly Tool 只有在 runtime retry policy 已配置且错误可重试时才重试，maxAttempts 封顶 3；write/dangerous 只尝试一次。
  • 超时来自 Capability exposure 的 timeoutMs 与 Run deadline，不存在统一默认 maxToolMs。
  • 非只读调用 dispatch 后被取消时可能成为 unknown_outcome：禁止自动重试，Run 失败，durable claim 保持待对账状态。

6.4 流式提交边界

  • 在首个对外可见流片段提交前，Provider 创建失败仍可以按候选和 retry 规则处理。
  • 一旦流已提交，后续错误必须沿当前流收敛，禁止无提示切换 Provider 后重新生成。
  • Provider delta 先成为内部 streaming event；Chat Facade 再将允许的事件映射为对外 SSE。
  • 取消信号贯穿排队、Provider 请求与当前 Capability 执行；取消不是可自动 failover 的 transient error。
不要混淆：create-stage retry 是同一 Provider 操作的有界重试；binding/route failover 是切换候选；readonly Tool retry 属于第五章 Capability 执行。三者的作用域、停止条件和副作用风险不同。

7.2 RuntimeRun 的恢复状态路径

queued
  └─ capacity reserved → assigned
       └─ active Instance claim → running
            ├─ normal completion → completed
            ├─ execution failure → failed

7.4 Recovery 边界

  • 每个 Run 被 claim 后才启动 cancellation monitor，并在该 attempt 结束时停止；它属于 attempt 生命周期，不是全局常驻任务。
  • running Run 的 Instance lease 过期后可进入 recovery_pending，随后由 recovery 流程重新进入 queued。
  • 同一 Run 再次丢失 Instance 时进入 terminal interrupted，避免无限恢复和资源放大。
  • 普通执行 attempt 的上限不是无条件 claim retry；第二次 attempt 只用于特定 requeue/recovery 路径。
  • 任何恢复都不能自动重试 unresolved non-readonly side effect。
  • Persistent DAG Recovery Coordinator 等待 run deadline、grace 与 claim expiry；没有已接纳调用或已有 durable terminal evidence 时才可安全重排。已接纳但缺少 durable terminal evidence 时标记 indeterminate 并中断，禁止盲目重放非只读调用。
资源放大边界：这些 gate 和状态顺序用于阻止重复执行、retry storm、replan storm、无限恢复和状态膨胀。恢复不能越过当前 owner fence，也不能把“尚无失败证据”误当成“可以安全重放非只读调用”。
